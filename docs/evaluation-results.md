## Reading the results

- **Constant ventilation is expensive and still not good enough.** Design
  flow day and night costs four times the energy of the other policies, and
  full lecture rooms still exceed 1000 ppm (65 % of their occupied minutes
  within limits, peak 1084 ppm): at design flow a full room settles right
  around 1000 ppm, as the sizing check predicted.
- **Reactive control already does almost all of it.** It meets NFR-1 with four
  minutes over 1000 ppm all week (in fika rooms, peak 1024 ppm), at the lowest
  energy.
- **Anticipation buys a little, for a little.** With perfect knowledge of the
  future, the oracle removes those four minutes and lowers the peak from 1024
  to 968 ppm, for 1.4 % more energy. Because the four runs saw exactly the
  same week, that 1.4 % is a real difference, not noise. The proposal (§7)
  said a small reactive-to-oracle gap would be a result worth reporting; here
  it is. The likely reasons: the damper can reach 1.5 × design flow within a
  few minutes, and lecture rooms (τ ≈ 12 min at design flow) catch up fast.
- **The predictor gets the oracle's air quality for 3.8 % more energy than
  reactive.** No occupied minute above 1000 ppm, peak 972 ppm. The 2.4 % it
  spends beyond the oracle is the price of an imperfect forecast: it
  ventilates fika rooms for a break on the days the break turns out small,
  and it reacts to the counter's occasional false "one person" in the live
  count.
- **The forecast warns ahead of fika breaks, but not of lectures.** In fika
  rooms it foresaw 87 % of arrivals (with false alarms in 23 % of quiet
  moments); "same as now" foresees none. In lecture rooms it foresaw none,
  because occupancysim puts each lecture in a random room every slot and day,
  so a room has no pattern to learn. A lecture timetable as an input (parked
  in architecture-options.md) is what would fix that.
- **Comfort is met everywhere.** Every occupied minute was within 20–24 °C
  under every policy, now that the heating starts before 07:00 and patrols
  don't count as occupancy.

## The predictor and sensor noise

The second evaluation first ran the predictive policy with a model that
expected at least one person in about **86 % of all 15-minute slots in every
room, at night too**. That run (`eval-predictive-v2`) used 25 % more energy
than reactive, most of it ventilating empty rooms.

The cause was how `predict.Train` treated the occupancy sensor's noise. The
sensor reports one person too many in about 5 % of its readings (FR-2: count
±1). Training took the **highest** reading in each slot of each day, then the
80 % quantile across the five days. With one reading per minute there are 15
readings per slot, so an empty room shows a false "1" in a slot on more than
half of the days (1 − 0.95¹⁵ = 54 %), and the quantile needs only two days of
five. The first evaluation trained on one reading per five minutes (three per
slot), where the same effect touched ~15 % of slots: it was there, but small.
So **more training data made the model worse**, the opposite of what we
assumed when we moved the training week to factor 120.

The fix (2026-10-08): a day's value for a slot is the 75th percentile of that
slot's readings, so a count has to show for about four minutes of fifteen to
register, and a forecast below half a person counts as an empty room. The
model was retrained on the same stored training week and only the predictive
run repeated; the other three runs don't use the model, and the weeks are
identical.

almost all the time.

## Compared with the first evaluation

The first evaluation (2026-10-01, runs `eval-*` without the suffix) differed
in three ways: the heating switched at 07:00 sharp, guards counted as
occupants, and each run sampled the day through its own coarse window (one
truth sample per two model-minutes, 99.6 % of samples equal between runs).

| | Constant | Reactive | Predictive | Oracle |
|---|---|---|---|---|
| 20–24 °C, first → second | 96.5 → 100.0 % | 97.2 → 100.0 % | 96.8 → 100.0 % | 97.0 → 100.0 % |
| … in lecture rooms | 84.0 → 100.0 % | 88.3 → 100.0 % | 85.7 → 100.0 % | 86.4 → 100.0 % |
| CO₂ ≤ 1000 ppm | 95.7 → 95.5 % | 100.0 → 100.0 % | 100.0 → 100.0 % | 100.0 → 100.0 % |
| Peak CO₂ | 1088 → 1084 ppm | 1015 → 1024 ppm | 972 → 972 ppm | 970 → 968 ppm |
| Energy, kWh | 24 677 → 25 285 (+2.5 %) | 6 136 → 6 282 (+2.4 %) | 6 758 → 6 521 (−3.5 %) | 6 213 → 6 370 (+2.5 %) |

- **Comfort** went from 96–97 % to 100 %: the misses were all cold samples
  during the setback (108 at night, 54 before dawn, 33 in the first hours of
  the day, in `eval-reactive`). Pre-heating removed the morning ones, and the
  night ones were patrols.
- **Energy** rose by about 2.5 % for three policies: that is what warming the
  rooms before 07:00 costs. The predictive policy fell by 3.5 % in spite of
  it, because its model no longer mistakes counter noise for people (the
  first evaluation's model had the same flaw in a milder form).
- **The ranking and the big effects did not change**: constant costs four
  times as much and still fails in lecture rooms; reactive is nearly as good
  as the oracle.

## Caveats

- **The building is a model we wrote.** The policies are compared against our
  own room physics; the result says as much about the model's time constants
  as about the controllers (proposal §8).
- **One seed, one week.** Day-to-day variation comes from occupancysim's
  generator; a second seed would show how stable the ranking is.
- **Factor 120.** The truth has every model minute, but a sensor polls four
  times per real second and a model minute lasts half a second, so a few
  readings are missed (0.01 % of CO₂ and temperature readings, 0.10 % of
  occupancy readings).
- **The control loop's timing is not reproducible**, by design: when a reading
  arrives and when a command lands depend on separate processes. The
  occupancy, and so the demand each policy faces, is identical between runs.
- **The heating's warm-up rate is assumed** (1.5 K/h); rooms are warm about an
  hour before 07:00.
- **Three runs are from 2026-10-06 and the predictive run from 2026-10-08.**
  That is sound because the simulated week is identical in all four (verified
  record by record) and the fix in between touches only the predictive
  policy. The run in between, `eval-predictive-v2`, is kept in storage as the
  evidence for the predictor flaw.

## Open items

- The live count still reacts to a single false reading: about 5 % of the
  predictive policy's decisions in an empty room ventilate for "one person".
  Requiring a count to persist for two readings would remove it, at the cost
  of a minute's delay for a real first arrival.
- Command latency (NFR-4) is not yet measured: actuators don't report when
  they reach a target.
- A second seed, and possibly a factor-60 run, to check the ranking holds.
- Learn the heating's warm-up rate per room instead of assuming it.
